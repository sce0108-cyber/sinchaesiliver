# [XSS] xss-2 문제 풀이 Write-up

## 문제 요약

Flask로 만들어진 "봇 기반 XSS" 문제. 서버는 헤드리스 크롬(`selenium`)으로 관리자 역할을 하는 봇을 띄워서, 진짜 FLAG 값이 담긴 쿠키(`{"name": "flag", "value": FLAG}`)를 들고 `/vuln?param=<내가 제출한 값>` 을 방문하게 만든다.

- `/flag` (POST): 내가 제출한 `param`을 봇이 방문 → 성공/실패 여부만 `good`/`wrong` alert로 알려줌 (FLAG를 직접 돌려주지 않음)
- `/vuln`: `param`을 화면에 그려주는 페이지. 여기가 실제 XSS가 터지는 지점(반사형 XSS로 추정 — `vuln.html` 템플릿 소스 자체는 확보하지 못해 동작으로만 추론함)
- `/memo`: `memo` GET 파라미터를 전역 변수에 계속 이어붙여서 화면에 보여주는 "메모장". 세션 구분이 없어서 **같은 오리진 안에서 데이터를 쌓아두는 저장소로 재활용 가능**하다는 게 이번 풀이의 핵심 트릭이었음.

쿠키에 `HttpOnly` 옵션이 없다는 것도 확인 (`read_url`에서 쿠키 객체에 `name`/`value`/`domain`만 있고 `httpOnly` 플래그가 없음) → JS에서 `document.cookie`로 그대로 읽을 수 있다는 뜻.

## 시도 1 — 실패: `<script>` 태그 직접 삽입

```
<script>alert(1)</script>
```

**결과**: 실행되지 않음 (`/flag` 응답이 `wrong??`).

**원인 (확인 필요)**: `<script>` 계열 페이로드가 막힌 이유 후보 두 가지 중 하나로 추정됨:
1. `vuln.html`이 Jinja2 기본 자동 이스케이프(autoescape)를 그대로 쓰고 있어서, `<script>`가 문자 그대로 `&lt;script&gt;`로 화면에 찍혀 텍스트로만 보이고 실행은 안 됨.
2. 서버 쪽에서 `"script"` 같은 특정 키워드를 걸러내는 블랙리스트 필터가 있음 (csrf-2.py의 `/vuln`에 있던 `xss_filter = ["frame", "script", "on"]`과 비슷한 방식일 가능성).

> ✏️ TODO: 실제 테스트 당시 페이지 소스보기(Ctrl+U)에서 `<script>`가 `&lt;script&gt;`로 보였는지, 아예 사라져 있었는지 기억나면 여기에 채워넣기. 전자면 (1)번(자동 이스케이프), 후자면 (2)번(키워드 필터)이 원인.

**배운 점**: `<script>` 자체가 막히더라도 "이 페이지가 사용자 입력을 화면에 그대로 반영한다"는 사실 자체는 변하지 않는다 → 다른 태그/이벤트 핸들러로 우회를 시도해볼 가치가 있다고 판단.

## 시도 2 — 성공: `<img>` + `onerror` 조합

```html
<img src="x" onerror="fetch('/memo?memo='+document.cookie)">
```

**왜 `<script>` 필터를 우회할 수 있었는가**:
- 이 페이로드에는 `script`라는 문자열이 어디에도 없다. `<script>` 태그 자체를 막는 필터/이스케이프가 있어도, **애초에 `<script>` 태그를 안 쓰고 JS를 실행시키는 방법**(이벤트 핸들러)을 쓴 것이 우회 포인트.
- 동작 원리:
  1. `src="x"` → 존재하지 않는 이미지 경로라서 로드가 100% 실패함
  2. 로드 실패 시 브라우저가 `onerror` 속성에 적힌 내용을 JS로 실행
  3. `document.cookie` = 봇이 들고 있는 쿠키 문자열(`flag=진짜FLAG값` 포함)을 읽어옴
  4. `fetch('/memo?memo=' + 그 값)` 으로 **같은 서버(same-origin)** 안의 `/memo` 라우트에 GET 요청을 보냄
  5. `/memo` 라우트가 받은 값을 전역 변수 `memo_text`에 그대로 이어붙여 저장
- 이후 `http://.../memo`에 직접 접속(파라미터 없이 GET)하면 방금 봇이 남긴 `flag=...` 줄을 눈으로 확인 가능.

**외부 서버(webhook.site 등) 대신 `/memo`를 쓴 이유**:
- 별도 인프라 없이 앱 자체 기능만으로 쿠키를 저장/열람할 수 있어 더 간단함
- 같은 오리진이라 CORS 정책에 걸릴 일이 없음 (외부 도메인으로 `fetch`를 보냈다면 CORS는 안 걸리지만 — 애초에 목적지가 공격자 서버라 응답을 읽을 필요도 없어서 상관없음. 다만 `/memo`처럼 "같은 앱 안의 다른 기능을 저장소로 재활용"하는 방식이 있다는 걸 기억해두면 다른 문제에도 응용 가능)

## 준비했지만 안 썼던 대안 (필터가 더 셌다면)

만약 따옴표(`"`)까지 필터링되는 상황이었다면 백틱으로 교체하는 방법도 염두에 뒀음:

```html
<img src=x onerror=location=`/memo?memo=`+document.cookie>
```

(실제로는 필요 없었지만, "따옴표까지 막히는 다음 문제"를 만났을 때 바로 꺼내 쓸 수 있도록 기록)

## 최종 정리 / 다음에 비슷한 문제 만나면 체크할 것

1. `<script>`가 막히면 → "무슨 방식으로 막혔는지"(자동 이스케이프 vs 키워드 필터)부터 페이지 소스로 확인하는 게 먼저다. 방식에 따라 우회법이 달라짐.
2. 키워드 블랙리스트는 보통 태그 이름이나 특정 단어 단위로 막기 때문에, **같은 결과를 내는 다른 문법**(이벤트 핸들러, 다른 태그)으로 쉽게 우회되는 경우가 많다.
3. 쿠키를 훔친 다음 "어디로 보낼지"는 꼭 외부 서버가 아니어도 된다 — 같은 앱 안에 로그성 기능(`/memo` 같은)이 있으면 그걸 저장소로 재활용할 수 있다.
4. 쿠키에 `HttpOnly`가 없는지 먼저 확인하는 습관 — 있으면 애초에 `document.cookie` 접근 자체가 안 되므로 다른 전략(예: 요청 자체를 대신 보내게 하는 CSRF성 접근)이 필요해진다.
